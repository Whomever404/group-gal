# 02 · 整体架构

> **结论先行**：本工程把「剧本数据」「引擎」「界面」「音频」拆成四层，用一条
> **单向依赖轴**串起来：`content → engine → ui ← main`，外加一个自成一体的 `audio`。
> 关键约束只有两条——**`engine/` 里没有一行 DOM，也不碰 `localStorage`**；
> **整个工程唯一允许碰 `localStorage` 的地方是 `ui/storage.ts`**。
> 剧本在书写时是「命名节点表」（DSL），在运行时是「扁平指令表」，两者之间只有
> `content/adapt.ts` 一个转换点——这就是整套架构能被无头测试的地方。

本篇描述的是**当前统一工程**（仓库根目录的 `src/`）的架构。旧的单文件 HTML 版本只作为历史资产保留，
详见文末「历史资产」。

---

## 1. 四层架构总览

```text
src/
├── content/   剧本数据层：DSL 剧本、角色表、结局文案、循环/分岔配置、DSL→扁平适配器
├── engine/    引擎层：零 DOM 的指令表解释器、校验器、存档序列化、路线图推导
├── ui/        界面层：QQ 群聊外壳 + galgame 面板，唯一碰 DOM 的地方
├── audio/     音频层：Web Audio 实时合成 BGM 与音效，离线可播
└── main.ts    组装层：把 ui 各块接成 Renderer，驱动 engine 的 run()
```

也不在 `src/` 下、但同属工程的两块：

| 位置 | 角色 |
|------|------|
| `vite.config.ts` / `index.html` / `package.json` | 构建与工具链（Vite + `vite-plugin-singlefile`），产出单文件 `dist/index.html` |
| `tools/` | 校验与测试脚本：`smoke.ts`（无头引擎测试）、`boot-check.mjs`（jsdom 端到端）、`*.py`（语料管线） |

### 1.1 各层职责与目录

| 层 | 目录 | 职责 |
|----|------|------|
| **content（剧本数据）** | `src/content/` | 用 DSL 写好的主线 `script.ts`、角色追加支线 `arcs/*.ts`、随机事件 `events.ts`、循环配置 `loop.ts`、角色表 `characters.ts`、结局文案 `endings.ts`、分岔入口 `route.ts`，以及 `adapt.ts`（唯一转换点）和入口 `index.ts`（收口 `SCRIPT` / `LABELS` / `ROUTE_ENDINGS`）。 |
| **engine（零 DOM 引擎）** | `src/engine/` | 类型定义 `types.ts`、指令表解释器 `runner.ts`、剧本图校验 `validate.ts`（含 CLI 入口 `validate.cli.ts`）、存档序列化/反序列化 `persist.ts`、羁绊与资质结算 `effects.ts`、路线图推导与关键节点快照 `route-map.ts`。 |
| **ui（界面）** | `src/ui/` | 外壳 `shell.ts`、聊天流 `chat.ts`、选项输入条 `composer.ts`、结局弹窗 `overlay.ts`、浮层 `toasts.ts`、Renderer 实现 `renderer.ts`，以及各面板：群成员 `drawer.ts`、回想 `backlog.ts`、存档 `saves.ts`、设置 `settings.ts`、路线图 `route-map.ts`、结局回收室 `gallery.ts`，还有剪影 `silhouettes.ts`、本地仓储 `storage.ts`。样式在 `src/styles/`（`tokens.css` / `title.css` / `chat.css` / `chrome.css`）。 |
| **audio（音频）** | `src/audio/bgm.ts` | 用 `OscillatorNode` / `GainNode` 现场合成 4 条 BGM 轨（`chat` / `night` / `tension` / `warm`）与 2 种音效；无 `AudioContext` 时安全降级为静默。 |
| **main.ts（组装）** | `src/main.ts` | 读设置、`mountShell()` 建外壳、创建各 UI 模块、拼出 `Renderer`、维护唯一的 `Session`、驱动 `run()`、接线所有按钮与存档。 |

### 1.2 禁止事项

| 层 | 必须遵守 | 原因 |
|----|----------|------|
| `engine/` | **禁止引用 DOM、`localStorage`、任何浏览器 API**；副作用只能经注入的 `Renderer` 发生；禁止 `import` 任何 `ui/` 模块。 | 让整张剧情图可在没有浏览器（Node / jsdom）的环境里跑完，是 `tools/smoke.ts` 与校验器的前提。引擎对 `content/characters.ts` 的读取是**只读的数据依赖**（拿 `CHARS` 判角色、取名字），不构成对界面的依赖。 |
| `content/` | 禁止 DOM 与 `localStorage`；不得 `import` `ui/`。只写「数据」与「适配」。 | 剧本必须能被校验器直接读；`adapt.ts` 只做纯数据变换。 |
| `ui/` | **唯一碰 DOM 的层**。其中**只有 `ui/storage.ts` 允许碰 `localStorage`**（且全程 `try/catch` 降级——存不了也不崩）。 | 把「不可信输入」与「浏览器环境」收拢到可审计的一两个文件里。 |
| `audio/` | 无 `window`（Node / SSR / 测试）时必须降级为静默而不是抛错。 | 构建产物要能在 jsdom 里被 `boot-check.mjs` 加载。 |

依赖方向（没有反向依赖）：`content → engine`（仅类型与 `buildLabelIndex`）、`ui → engine + content`、`main → ui + engine + content + audio`。

## 2. 两套剧本模型：DSL 与扁平剧本

同一份剧本在工程里并存两种表示，各有明确分工（定义都在 `src/engine/types.ts`）：

| | **DSL（书写格式）** | **扁平剧本（执行格式）** |
|---|---|---|
| 类型 | `Script = Readonly<Record<string, DslNode>>` | `FlatScript = readonly FlatNode[]` |
| 形态 | **命名节点表**：每个节点一个 id，节点内显式写 `next` / `o`（选项）跳转 | **指令表**：一串线性节点，指针 `ip` 从头往后走 |
| 谁在写/读 | 剧本作者在 `content/script.ts`、`content/arcs/*.ts` 里写 | 引擎 `runner.ts` 只认这一种 |
| 好处 | 写作友好：命名节点、显式跳转、中文注释、字段缩写（`m`/`d`/`b`/`l`/`o`/`fx`） | 可机械校验：线性 `ip` + 绝对下标，可达性、跳转、快照都能被程序验证 |

DSL 节点长这样（`DslNode`）：

```ts
interface DslNode {
  m?: 'chat' | 'avg';      // 呈现模式：聊天流 / 场景独白
  d?: string;              // 顶栏章节名
  bgm?: string;            // 切曲（daily/night/tense/end）
  c?: string | null;       // 场景立绘角色
  b?: readonly DslChatLine[];   // chat 行 [角色key|'#', 文本]
  l?: readonly DslAvgLine[];    // avg 行 [角色key|null|'#', 文本]
  o?: readonly DslChoice[];     // 选项 [文案, 跳转, fx?, once?]
  next?: string;                // 线性推进目标
  fx?: DslFx;                   // 节点自带加成（只结算一次）
  j?: 'branch';                 // 分岔之夜：按锁定对象/羁绊最高者走角色线
  loop?: boolean;               // 回合循环中枢
  hub?: boolean;                // 一次性 hub（保留位，当前剧本未用）
}
```

扁平节点则是一串**判别联合** `FlatNode`（`label` / `say` / `sys` / `note` / `card` / `stage` / `chapter` / `bgm` / `aff` / `stat` / `set` / `goto` / `choice` / `hub` / `loop` / `branch` / `be` / `ge`）。其中两个「数据驱动的分支节点」值得单独记：

- `loop` 节点自带一份 `LoopConfig`（候选 / 本命支线 / 随机事件池 / 阈值 / 推进去向）；
- `branch` 节点自带一份 `BranchConfig`（各角色线入口 / 空気过高时的 Bad End / 平票优先序）。

把配置**放进节点本身**，是为了让校验器能像看 `choice` 一样看见 `loop` / `branch` 的每一条边（`validate.ts` 的 `gotoTargets()` 正是这么做的）。

### 2.1 `adapt.ts`：唯一转换点

`content/adapt.ts` 是 DSL → 扁平剧本的**唯一**转换实现。规则（见 `adaptNode()`）：

- 每个 DSL 节点先产出一个 `label` 节点，再按顺序追加 `chapter` / `bgm` / 立绘先导 / 内容行 / 选项 / 跳转；
- 节点自带 `fx` → 紧跟 `label` 的 `aff` / `stat` 节点（只结算一次）；
- `chat` 行 → `say` / `sys`；`avg` 行 → `say` / `sys` / `note`，并按 `c` 生成 `stage`（每个节点先重置舞台）；
- 选项携带的 `fx` → 选项上的 `eff` / `stat`；**纯动作型选项**（文案整体被括号包住，如「（先不说话……）」）标 `act`，不当作发言；
- 说话人化名：DSL 里的 `you` → 扁平剧本的 `me`；
- `j:'branch'` / `loop:true` → `branch` / `loop` 节点；
- `__end_*` / `__ge_*` 目标 → 在扁平表末尾统一生成 `be` / `ge` **端子节点**（`collectTerminals()`），让「剧本数据」与「机械生成的端子」在结构上分开。

> **为什么必须两者分开**：如果只剩扁平表，作者要手写绝对下标和 `goto` 数字，写不动也改不动；如果只剩 DSL，
> 引擎就得在每个节点上反复做「找跳转、查表、算下标」，且可达性、快照这些机械检查无处落脚。
> 因此让**写作**用命名表的便利，**执行**用指令表的可验证性，中间只保留一个转换点。
> 转换后 label 存的是**绝对下标**，所以「顺序即执行顺序」——调整节点顺序后必须重跑 `npm run check:script` 确认可达性。

## 3. 数据流

### 3.1 构建期：从 `NODES` 到 `SCRIPT`

`content/index.ts` 是全工程**唯一**知道「剧本怎么拼起来」的地方，因此不存在两处拼接顺序漂移的可能：

```ts
// content/script.ts —— 把基础剧本、事件池、15 条角色支线合并成完整命名节点表
export const NODES: Script = { ...BASE, ...EVENT_NODES, ...nanao_ARC, /* …共 15 个 arc… */ };

// content/index.ts —— 展平并建索引
export const SCRIPT: FlatScript = buildFlat(NODES);           // content/adapt.ts
export const LABELS: LabelIndex = buildLabelIndex(SCRIPT);    // engine/validate.ts（复用同一实现）
```

- `SCRIPT`：扁平剧本（执行格式），校验器、引擎、无头测试都从这里取。
- `LABELS`：`label 名 → 下标` 的索引，供 `goto` 解析和路线图判定入口。
- `ROUTE_ENDINGS`：15 条角色线结局的标题与正文，**直接取自 `ge_<key>` 场景节点**（也就是玩家真正读到的那段收尾），因此不会出现「结局卡与正文不一致」。

### 3.2 运行期：`run(session, env, renderer)`

`engine/runner.ts` 的 `run()` 是唯一的驱动循环：就地修改 `session.state` / `session.ip` / `session.history`，所有界面副作用经 `Renderer` 转发。

```ts
export async function run(session: Session, env: GameEnv, r: Renderer): Promise<void> {
  while (session.ip < script.length) {
    if (env.shouldStop?.()) return;
    const node = script[session.ip]!;
    env.onNode?.(session.ip, node);   // 回调时 ip 仍指向本节点
    session.ip++;
    switch (node.kind) { /* … */ }
  }
}
```

`GameEnv` 注入四项内容加两个可选钩子：`script` / `labels` / `chars` / `beData`，以及 `onNode`（每个节点**执行前**回调，自动存档靠它）与 `shouldStop`（读档时作废仍在跑的旧 `run`）。

节点到 UI 的落点：

| FlatNode | 引擎动作 | 经 Renderer 落到 |
|----------|----------|------------------|
| `say` / `sys` / `note` | 推入 `session.history`，再展示 | `r.say` / `r.sys` / `r.note` → `chat.ts` |
| `card` / `stage` | 展示 | `r.card` / `r.stage` → `chat.ts`（舞台剪影） |
| `chapter` / `bgm` | 展示 | `r.setChapter` → 顶栏；`r.bgm` → `BGM.set` |
| `aff` / `stat` | `effects.ts` 结算 → 新 `state` | `r.affToast` / `r.statToast` → `toasts.ts` |
| `choice` | `askChoice` 作答 → 结算 → `ip = goto` | `composer.ts` |
| `hub` | 过滤已触发的 `once` 项 → 作答 → 结算 → `ip = goto` | `composer.ts` |
| `loop` | 按 `state.target` / 阈值动态生成选项（首轮全员候选，锁定后只出对象支线 + 随机事件 + 推进） | `composer.ts` |
| `branch` | 空気≥3 → `beWhenAirless`；否则按锁定对象或羁绊最高者跳角色线 | `overlay.ts`（BE）/ 跳转 |
| `be` / `ge` | 记录回收 → 结束本次 `run` | `r.showBE` / `r.showEnding` → `overlay.ts` |

### 3.3 存档流

序列化与**防御性**反序列化在 `engine/persist.ts`（纯逻辑、零 DOM）；读写与降级在 `ui/storage.ts`（全工程唯一碰 `localStorage` 的地方）。

```text
写：main.ts snapshotSession()
      → ui/storage.ts writeSlot(id, session)      // 加 savedAt 元数据
      → engine/persist.ts serializeSession()      // 纯 JSON
      → JSON.stringify → localStorage.setItem

读：ui/storage.ts readSlot(id)
      → JSON.parse
      → engine/persist.ts migrateSave(parsed, SCRIPT.length)
          ├─ 老存档经 upgradeState() 补齐 stats/target/turn/unlocked
          └─ deserializeSession() 逐字段校验；任何畸形一律返回 null，绝不抛错、绝不污染原型
      → 合法 Session → main.ts loadSession()（重放历史 + 从指针续跑）
```

- 存档单位是 `Session`：`state` + `ip`（指向下一个待执行节点）+ `history` + `progress`，四者都是纯 JSON。
- `writeSlot` 里「不可信的 `localStorage`」被当作**不可信输入**处理：坏存档只会读不出来，不会白屏。
- 自动存档在进入 `choice` / `hub` / `loop` / `branch` 节点时写入；手动槽为 3 个（`s1` / `s2` / `s3`），自动存档 id 为 `auto`。
- 设置（`bgm` / `speed`）走独立的 `SETTINGS_KEY`，逐字段校验并回落，单个字段坏了不丢其它字段。

## 4. Renderer 接口：引擎与 DOM 的唯一接缝

`Renderer`（定义于 `engine/types.ts`）是引擎**唯一**的出口，也是引擎与 DOM 之间**唯一的接缝**。方法以 `types.ts` 为准：

| 方法 | 签名 | 落到哪 |
|------|------|--------|
| `setChapter` | `(title: string) => void` | 顶栏章节名（`main.ts` 注入的 `topbar`） |
| `say` | `(who, text) => Promise<void>` | `chat.ts` 气泡（`who === 'me'` 走右侧气泡） |
| `sys` | `(text) => Promise<void>` | `chat.ts` 居中系统消息 |
| `note` | `(text) => Promise<void>` | `chat.ts` 居中旁白 |
| `card` | `(who: CharKey) => Promise<void>` | `chat.ts` 角色群名片 + 同步舞台剪影 |
| `stage` | `(who: CharKey \| null) => void` | 右下角常驻剪影（比 `card` 轻） |
| `bgm` | `(track: TrackName) => void` | `BGM.set()` |
| `affToast` | `(items) => void` | `toasts.ts` 羁绊浮层（**引擎已结算，这里只展示**） |
| `statToast` | `(items) => void` | `toasts.ts` 资质浮层（同上） |
| `toast` | `(text) => void` | `toasts.ts` 通用浮层 |
| `askChoice` | `(prompt, options) => Promise<number>` | `composer.ts` 返回被选项下标 |
| `askHub` | `(prompt, options) => Promise<number>` | `composer.ts`（选项已由引擎过滤 `once`） |
| `showBE` | `(id: BeId) => Promise<void>` | `overlay.ts` Bad End 弹窗 |
| `showEnding` | `(resolution, session) => Promise<void>` | `overlay.ts` 路线结局弹窗 |
| `delays` | `readonly DelayPolicy` | 等待时长；**可直接改 `fast` 字段**，快进即时生效。它的可选方法 `wait(ms)` 由 `main.ts` 实现为**可被打断的等待**——点击消息流或按空格 / 回车即「推进」，引擎因此不必知道 DOM 的存在 |

`ui/renderer.ts` 的 `createRenderer(deps)` 把这些方法接到 `chat` / `composer` / `overlay` / `toasts` 与 `BGM` 上。它刻意**不**维护顶栏数值（成员 / 水群值 / 资质）——这些由 `main.ts` 在每个节点前从 `session.state` 整体同步一次，避免「UI 自己算一份」与引擎数值漂移。

**无头跑通整张剧情图**正是靠换掉这个接缝：`tools/smoke.ts` 里定义一个 `FakeRenderer implements Renderer`，只用数组记录调用序列（`hubAsks` / `choiceAsks` / `endings` / `beShown` / `said` …），`delays` 全为 0、`fast: true`，再用一个 `strategy` 回调决定每个选择题怎么选。于是同一份 `run()` 不加载任何 DOM 就能把 15 条角色线、空気结局、存档往返全部断言一遍（`npm run smoke`）。

与之互补的是 `tools/boot-check.mjs`：它用 jsdom 真正加载构建产物 `dist/index.html`，走到回合循环，验证**真实** UI（外壳挂载、选项作答、复读彩蛋、回收室、运营规则）。

## 5. 界面结构

### 5.1 启动链路

```text
index.html（Vite 开发入口）
  ├─ 一段 setTimeout(1200ms) 兜底脚本：若始终没出现 #title，就显示 #boot-fallback
  └─ <script type="module" src="/src/main.ts">
        └─ main.ts
             ├─ mountShell(#app)        // ui/shell.ts：一次性写入静态外壳，返回元素引用
             ├─ createChatView / createComposer / createOverlay / createToasts
             ├─ createRenderer(deps)    // 组装 Renderer
             └─ 接线所有按钮 + 存档
```

- **`index.html` 是开发入口，不能直接双击**：缺少 Vite 或构建产物时模块加载失败，`#boot-fallback` 提示才显示出来。构建产物里启动成功会先换掉 `#app`，因此提示不会闪现，只有真失败时才露出来。
- **`mountShell()` 生成静态外壳**：`SHELL_HTML` 是一段静态字面量（不含任何外部数据），建出 `#title` / `#game` / `#stageSil` / `#toasts` / `#drawer` / `#panel` / `#overlay`，并通过 `need()` 取回所有必需元素的引用。来自剧本或角色的文本一律经 `chat.ts` 的 `esc()` 转义后再拼入，绝不直接 `innerHTML` 外部数据。
- **`main.ts` 接线**：把外壳的元素引用分发给各 UI 模块，并把 `overlay` 的重开/回标题、顶栏 `⋯` 菜单、各面板开关接到对应函数上。全工程只有一份可变的 `Session`，`run()` 与 `main.ts` 共享同一个对象引用（只改字段，不重新赋值）。

### 5.2 两套视觉语汇

`shell.ts` 在结构上就把两种界面分开：

| 区域 | 语汇 | 说明 |
|------|------|------|
| `#game` 内的顶栏 / 消息流 / 输入区 | **手机 QQ 群聊客户端** | 石墨灰深浅层次、自己的 QQ 蓝气泡、蓝色 `@提及`；选项以「从输入框上方弹出的候选」呈现 |
| `#title` / `#overlay` / `#panel` | **galgame（叙事）** | 近黑靛底、暖纸色正文、黄铜色强调；大标题用中文衬线；全屏暗化 + 居中文本框 |

样式令牌在 `tokens.css` 里分成两个命名空间：`--qq-*`（群聊）与 `--vn-*`（叙事），**刻意不共享颜色**。

### 5.3 桌面三栏 / 窄屏单栏

同一份外壳 DOM，靠断点切换：

| 断点 | 行为 |
|------|------|
| `≥ 900px`（桌面） | 显示**三栏**：最左竖导航 `qq-rail`（60px）＋ 会话列表 `qq-convs`（248px）＋ 会话区 `qq-main`；输入条里多两个 `wide-only` 工具图标 |

### 5.4 标题页、结局页与各面板

- **标题页 `#title`**：galgame 排版——中文衬线大标题、竖排菜单、底部一排角色剪影合影（`main.ts` 注入，纯装饰）。按钮为「开始游戏 / 结局回收室 / 音乐 / 关于」。
- **结局页 / 关于 `#overlay`**：全屏暗化 + 居中文本框，正文按空行**逐段**淡入；`be-ov` 用冷钢蓝，`end-ov` 用暖黄铜。Bad End 与好结局由 `engine` 判定后经 `EndingResolution` 传入，`overlay.ts` 只负责展示。
- **面板 `#panel`**（VN 面板观感，与抽屉共用容器，可加宽）：

| 面板 | 渲染器 | 内容 |
|------|--------|------|
| 群成员（抽屉，非面板） | `ui/drawer.ts` | 15 名可攻略角色的羁绊条与阶段（无视 / 眼熟 / 嘴替 / 宝宝 / 沦陷）＋ 一行「助攻 / 反派」占位 |
| 回想 | `ui/backlog.ts` | 逐条列 `session.history`（说话人用主题色）——它是「历史可序列化」的第一个消费者 |
| 存档 | `ui/saves.ts` | 3 个手动槽 + 自动存档；删除走**内联二次确认**（不用 `confirm()`） |
| 设置 | `ui/settings.ts` | 音频（BGM 开关）/ 文字（慢·普通·快）/ 数据（清除全部存档）三组 |
| 路线 | `ui/route-map.ts` | 分列流程图：坐标由 `engine/route-map.ts` 纯逻辑算出，UI 只换算像素并画正交连线 |
| 结局回收室 | `ui/gallery.ts` | 23 个 Bad End + 15 条好结局的收集进度，未解锁只显示占位 |

其中**路线图**有一处值得记的设计：未到达的真实节点一律不画；但已达的抉择点上，每个选项都画成一条分支——通向未达节点的那条画成不可点击的幽灵「?」空位，只表示「这里有路没走过」，不透露内容。这是「渐进揭示（不剧透）」与「要看见分支」两条要求的折中，也是渐进揭示规则的唯一例外。

## 6. 两处刻意的不对称

这不是疏漏，而是刻意的取舍。

**其一：写作用命名节点表，执行用扁平指令表（§2）。** 同一份剧本并存 DSL 与 `FlatScript` 两种表示，中间只留 `adapt.ts` 一个转换点。写作时人要的是「命名 + 显式跳转 + 中文注释」，执行时机器要的是「线性 `ip` + 绝对下标 + 可机械校验」。把两者强行统一成一种，必然牺牲其中一端。

**其二：数值主权的分裂。** 引擎负责**结算**羁绊（`aff`）与资质（`stat`），并只把**变化量**交给 `Renderer`（`affToast` / `statToast`）去展示；但顶栏的**总量**（成员数 / 水群值 / 五项资质）完全不经过 `Renderer`，而是由 `main.ts` 在每个节点执行前从 `session.state` 整体同步一次。这样「浮层」和「顶栏」走了两条不同的路：浮层报的是「刚刚发生了什么」，顶栏报的是「现在是多少」——两者都不允许 UI 自己去算，从而不会与引擎数值漂移。

### 数量核对

以 `npm run check:script` 的输出为准：

```bash
$ npm run check:script
角色 16（可攻略 15）　·　节点 1249（label 165）　·　坏结局 23　·　角色线 15
剧本校验通过：1249 个节点，0 个警告
```

即：**扁平剧本 1249 个节点、165 个 label、16 个角色（15 可攻略 + 1 反派）、23 个 Bad End、15 条角色线**。该命令是 `npm run build` 的前置步骤——剧本写坏（跳转拼错、角色键拼错、Bad End 缺文案、节点不可达）会让构建失败，而不是等玩家踩到。
