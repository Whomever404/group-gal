# 03 · 核心引擎与关键函数

> 本文以整合后工程的 **TypeScript 重写版引擎**（`src/engine/`）为准，
> 描述「引擎是怎么跑起来的」：唯一的驱动函数 `run()`、可变会话 `Session`、
> 回合循环与分岔、结局、结算、复读、剧本校验与存档迁移。
> 上层装配（谁在什么时机调用这些函数）见 `src/main.ts`。
>
> 一句话结论：**引擎是一个线性 `ip` 指针 + 指令表的解释器**——`run()` 沿
> 扁平剧本 `FlatScript` 逐节点推进，就地改写可变的 `Session`，所有界面副作用
> 经 `Renderer` 出海；分支节点（`choice` / `hub` / `loop` / `branch`）把去向写在
> 自身配置里，因此校验器能像看普通跳转一样看见剧本的每一条边。

---

## 1. 引擎总览

引擎层零 DOM、零网络，纯逻辑，全部落在 `src/engine/`：

| 文件 | 角色 |
|------|------|
| `runner.ts` | 主循环 `run()`、节点解释器、回合循环 / 分岔 / 结局分支、结算与复读相关工具 |
| `types.ts` | 全部类型：`FlatNode`、`Renderer`、`Session`、`GameState`、`DelayPolicy`、`EndingResolution` 等（无运行时代码） |
| `effects.ts` | 数值结算与元数据：`SCHEMA_VERSION`、`applyEff` / `applyStat` / `stageOf` / `applyRepeat` / `unlockEnding` / `topHero`、初值工厂 |
| `validate.ts` | 剧本静态校验：起始 / 重复 label、跳转目标、角色键、BE 文案、`loop` / `hub` 去重键、可达性、flag 使用 |
| `route-map.ts` | 路线图：从剧本推导有向图、布局（渐进揭示 + 幽灵节点）、进度记录与快照 |
| `persist.ts` | 存档序列化与**防御性**反序列化、版本迁移 |
| `validate.cli.ts` | 校验入口，`npm run check:script` 调用，也是 `npm run build` 的前置步骤 |

数据侧只给引擎两样东西：**扁平剧本**（`FlatScript`，由 `content/adapt.ts` 从 DSL 生成）
与**索引**（`LabelIndex`，来自 `content/index.ts` 的 `LABELS`）。引擎不含任何剧本内容。

一次推进的骨架：

```ts
while (session.ip < script.length) {
  if (shouldStop?.()) return;
  const node: FlatNode = script[session.ip]!;
  onNode?.(session.ip, node);
  session.ip++;
  switch (node.kind) { /* 见 §3 */ }
}
```

## 2. 节点解释器 `run()`

`run(session, env, r)` 是唯一的驱动函数，`async` 返回 `Promise<void>`。它从
`env` 里取出 `script` / `labels` / `chars` / `beData` / `onNode` / `shouldStop`，
然后进入上方那个 `while` 循环。

**`ip` 语义 = 指向「下一个待执行节点」。** 调用前 `ip = 0` 表示从头开始；
循环体先读 `script[session.ip]`，回调，再 `session.ip++`，最后按 `node.kind` 分派。
返回时 `ip` 停在终止节点（`be` / `ge`）之后，或剧本末尾。

**`session` 是可变工作副本。** `run()` 直接就地修改 `session.state` / `session.ip` /
`session.history`（都是普通字段赋值，而非返回新对象）。`main.ts` 里
`let session: Session = {...}` 在 `startGame` / `loadSession` / `jumpTo` 中也只**逐字段换内容**
（`session.state = ...`、`session.ip = ...`），绝不 `session = ...` 整体重新赋值——
因为 `run()` 持有的是同一个对象引用，一旦重新赋值，引擎与界面两侧会永久分叉。
`effects.ts` 的 `applyRepeat` 也遵循同一约定（见 §8）。

三个 `GameEnv` 成员的关键时序：

| 成员 | 时机 | 为什么重要 |
|------|------|-----------|
| `onNode(ip, node)` | 每个节点**执行前**，参数是该节点自身下标 | `run` 是先回调再 `ip++`，所以回调里读到的 `session.ip` 正指向该节点。自动存档靠它在**选择点**存下指针；若改到执行后再回调，读档会跳过那个选择 |
| `shouldStop()` | 每个节点开始前询问「是否中止」 | 返回 `true` 时 `run` 立即返回。用于读档：载入新存档必须作废仍在跑的旧 `run`，否则它会在延迟结束后继续就地改同一个 `Session`，与新 `run` 打架。`main.ts` 用自增的 `runToken` 实现（`shouldStop: () => token !== runToken`） |

两个辅助函数：

- `delayFor(r, ms)`：读 `r.delays.fast`，为 `true` 时把等待钳到 `FAST_CAP_MS = 60`；
  钳后 `<= 0` 直接 `Promise.resolve()`；否则优先交给 `r.delays.wait(ms)`，
  没有实现 `wait` 时才退回普通 `setTimeout`。`wait` 是可被界面**打断**的等待，
  「点击 / 空格推进」就是调用打断函数，因此引擎仍然零 DOM。
- `resolveTarget(labels, label)`：查 `labels[label]`，缺失则抛 `UnknownLabelError`
  （`goto 目标不存在，请跑 npm run check:script`）。所有跳转都经它，未知 label 不会静默串线。

默认计时由 `DEFAULT_DELAYS` 给出（`me: 280 / msg: 520 / sys: 560 / note: 680 / card: 760`，`fast: false`）。

## 3. 全部节点种类

`FlatNode` 共 18 种。下表逐条说明作用、是否产生等待（`await`）、是否写入历史 `session.history`：

| kind | 作用 | 等待 | 写历史 |
|------|------|------|--------|
| `label` | 命名锚点，无副作用；`goto` / 选项都跳到它。`labels` 索引由它建立 | 否 | 否 |
| `chapter` | `r.setChapter(title)` 切换顶栏章节名 | 否 | 否 |
| `say` | 角色或 `me` 发言。`await r.say(who, text)` 后按 `who === 'me' ? delays.me : delays.msg` 延时 | 是 | 是（`{kind:'say', who, text}`） |
| `sys` | 系统消息。`await r.sys(text)` + `delays.sys` | 是 | 是（`{kind:'sys', text}`） |
| `note` | 旁白 / 独白。`await r.note(text)` + `delays.note` | 是 | 是（`{kind:'note', text}`） |
| `card` | 角色名片卡。`await r.card(who)` + `delays.card` | 是 | 否 |
| `stage` | 舞台立绘：设置 / 清除右下角剪影，不产生消息 | 否 | 否 |
| `bgm` | `r.bgm(track)` 切换曲目 | 否 | 否 |
| `aff` | `settle(session, chars, r, { eff })` 结算一次羁绊 | 否 | 否 |
| `stat` | `settle(session, chars, r, { stat })` 结算一次资质 | 否 | 否 |
| `set` | 置位一个 flag：`flags[flag] = true`（不可变式重写 `state`） | 否 | 否 |
| `goto` | `session.ip = resolveTarget(labels, label)` | 否 | 否 |
| `choice` | 弹选项。`await r.askChoice`，记发言 / 旁白、`settle`、跳到 `opt.goto` | 是 | 是（见下） |
| `hub` | 一次性选项中枢。过滤掉已触发的 `once` 项、`await r.askHub`、写去重键、`settle`、跳转 | 是 | 否 |
| `loop` | 回合循环中枢，动态生成选项（§4） | 是 | 否 |
| `branch` | 分岔之夜，按状态选路（§5） | 视情况 | 否 |
| `be` | Bad End 端子：`showBE` 后 `return`（§6） | 是 | 否 |
| `ge` | 角色线好结局端子：`showEnding` 后 `return`（§6） | 是 | 否 |

`choice` 的历史写入有个细节：纯动作型选项（`opt.act === true`，文案是括号）以
**旁白**记入（`{kind:'note', text}` + `r.note`），不当作「我」发出的消息；否则记
`{kind:'say', who:'me', text: spoken}` 并 `r.say('me', ...)`，其中 `spoken = opt.say ?? opt.label`。
之后一律 `settle` + `session.ip = resolveTarget(labels, opt.goto)`。

`hub` 的要求：先 `available = node.options.filter(o => !isDone(...))`，若为空则
`throw new Error('hub 没有可用选项（全部 once 选项已触发且无兜底分支）')`；被选中的
`once` 项会写 `state.hub[opt.id] = true`（`isDone(o)` 即 `o.once === true && state.hub[o.id] === true`）。

## 4. 回合循环（夜间运营）

第二章「群日常」的中枢。选项由 `loopOptions(state, node)` 按当前状态动态生成，随后在
`case 'loop'` 里落锁定、写去重键、推进 `turn`。

### 4.1 `loopOptions()` 的完整规则

选项 `id` 同时是 `state.hub` 的去重键：

| 阶段 | 生成规则 | 选项 id |
|------|---------|---------|
| **首轮**（`!state.target` 或该 key 无支线） | 遍历 `cfg.candidates`，每个候选一条，全部 `once: true`、`goto: c.entry`（15 条全员候选） | `pick_<key>` |
| **已锁定**：本命支线 | 遍历 `cfg.arcs[key]`，跳过 `state.hub['seg'+i+'_'+key]` 已触发的，其余 `once: true`、`goto: seg.entry` | `seg<i>_<key>` |
| **已锁定**：随机事件 | 遍历 `cfg.events`，最多 `cfg.eventsPerTurn` 条，跳过 `state.hub['ev_'+ev.id]` 已触发的 | `ev_<id>` |
| **追加「推进主线」** | 当 `bond >= cfg.threshold`，或本命支线走完（`done >= segments.length`），或当前一个选项都没有（`opts.length === 0`）时，追加一条 | `adv` |

其中 `bond = state.aff[key] ?? 0`，`done` = 已触发的本命支线段数（按 `seg<i>_<key>` 计数）。
`adv` 的 `goto` 是 `cfg.advance`（指向第三章 · 躲猫猫之夜）。

校验器对 `loop` 的去重键也照同样的规则检查（见 §9）。

### 4.2 `case 'loop'` 如何落地

```ts
const turn = session.state.turn + 1;                 // 本次进中枢即 +1
const all = loopOptions(session.state, node);
const available = all.filter(o => !isDone(session.state, o));
if (available.length === 0) throw new Error('回合循环没有可用选项（支线与事件都已触发）');
const prompt = session.state.target
  ? turnPrompt(session.state, cfg.prompt, cfg.threshold, cfg.arcs[session.state.target]?.length ?? 0)
  : `第 ${turn} 个晚上 · 群里 ${cfg.candidates.length} 个人都值得深挖，先挑一个？`;
session.state = { ...session.state, turn };
```

选完之后：

- 若 `opt.id.startsWith('pick_')`：在 `cfg.candidates` 里找到该候选，写
  `target = cand.key`，并把 `aff[cand.key]` 加 `cfg.lockBonus`（**锁定加成一次性**），
  再 `r.toast('已锁定攻略对象：<emoji> <name>（羁绊 +<lockBonus>）')`。
- 否则若 `opt.once`：把 `state.hub[opt.id] = true`（写去重键）。
- 最后 `settle(...)` + `session.ip = resolveTarget(labels, opt.goto)`。

**顶栏文案**由 `turnPrompt(state, base, threshold, segments)` 拼出：

```ts
`${base}　｜　${ch.emoji} ${ch.name}　羁绊 ${bond}/${threshold}　本命支线 ${done}/${segments}　｜　第 ${state.turn} 个晚上`
```

其中 `bond` 被 `Math.min(aff, threshold)` 夹住（显示不会超过阈值），
`done` 按 `seg<i>_<key>` 统计已触发的本命支线段数。

> 配置数据来自 `content/loop.ts`（`THRESHOLD` / `LOCK_BONUS` / `EVENTS_PER_TURN` /
> `CANDIDATES` / `ARC_STEPS` / `LOOP_ADVANCE`）与 `content/events.ts`，由 `content/adapt.ts`
> 组装成节点自带的 `LoopConfig`。

## 5. 分岔之夜

`case 'branch'` 的判定顺序**先空気、后锁定对象**：

```ts
const airless = session.state.stats.q >= 3;
if (airless) { await showBE(session, r, cfg.beWhenAirless); return; }
const who = (session.state.target && cfg.routes[session.state.target])
  ? session.state.target
  : topHero(session.state, cfg.fallbackOrder);
session.ip = resolveTarget(labels, cfg.routes[who]!);
```

1. **空気（`stats.q`）≥ 3** → 直接落 `cfg.beWhenAirless` 指定的 Bad End（脚本里是 `b81`
   「第 81 人」），`run` 随即 `return`。
2. 否则：**已锁定攻略对象**（`state.target` 有值且 `routes` 里有它）→ 走该对象。
3. **未锁定** → `topHero(state, cfg.fallbackOrder)` 取羁绊最高者；平票按
   `fallbackOrder` 顺序**靠前者胜**（`topHero` 里 `>` 比较、初值 `-1` 保证稳定）。

`BranchConfig` 的字段：`prompt` / `routes` / `beWhenAirless` / `fallbackOrder`，
分别来自 `content/route.ts` 的 `ROUTE_START` / `PRIORITY` 与固定值 `'b81'`。

## 6. 结局

两种终局节点都在解锁后交给 `Renderer`，并让 `run` 立即 `return`：

```ts
case 'be': {
  if (!(node.id in beData)) throw new Error(`Bad End 缺少文本：${node.id}`);
  await showBE(session, r, node.id);
  return;
}
case 'ge': {
  session.state = unlockEnding(session.state, 'ge_' + node.key);
  await r.showEnding({ kind: 'route', key: node.key }, session);
  return;
}
```

- **`be`**：先校验文案存在（缺则抛错），再走 `showBE(session, r, id)`。
  `showBE` 内部先 `unlockEnding(state, id)` 记账，再 `await r.showBE(id)`。
- **`ge`**：解锁键是 `'ge_' + node.key`，然后
  `r.showEnding({ kind: 'route', key: node.key }, session)`；`EndingResolution` 的
  两种取值即 `{ kind: 'be', id }` 与 `{ kind: 'route', key }`。

**`unlockEnding` 与 `state.unlocked`**：`unlockEnding(state, key)` 是纯函数——
若 `key` 已在 `unlocked` 里就原样返回，否则追加一条新状态。Bad End 记的是 `<id>`
（如 `b24` / `b81`），好结局记的是 `ge_<key>`。**结局回收室直接读 `state.unlocked`**：
`ui/gallery.ts` 用 `beIds.filter(id => state.unlocked.includes(id))` 与
`GE_SLOTS.filter(k => state.unlocked.includes('ge_' + k))` 统计收集进度并给卡片点亮。

`Renderer` 侧由 `createRenderer` 转译：`showBE` → `BGM.set('tension')` + `overlay.showBE(id)`；
`showEnding` → `BGM.set('warm')` + `overlay.showEnding(resolution, session)`。

## 7. 结算

选项 / 节点上的加成统一经 `settle()`，它把引擎结算与界面汇报分开：

```ts
function settle(session, chars, r, goto?): void {
  if (!goto) return;
  if (goto.eff)  { const { state, toasts } = applyEff(session.state, goto.eff, chars);  session.state = state; if (toasts.length) r.affToast(toasts); }
  if (goto.stat) { const { state, toasts } = applyStat(session.state, goto.stat);        session.state = state; if (toasts.length) r.statToast(toasts); }
}
```

`applyEff` 与 `applyStat` 的差别：

| | `applyEff`（羁绊） | `applyStat`（资质） |
|---|---|---|
| 门控 | **受 `hero` 门控**：角色不存在、非 hero（如反派 `moku`）、或 delta 为 `undefined` / `0` 一律跳过 | 无角色概念，只跳过 `undefined` / `0` |
| 下限 | `Math.max(0, aff + delta)` | `Math.max(0, stat + d)` |
| 浮层 | `AffToastItem { who, delta }` | `StatToastItem { key, delta }` |
| 汇报值 | **原始 delta**，不是实际增量 | 原始 delta |

两者都是纯函数，只有在真的发生变化时才返回新 `state`（否则原样返回、`toasts` 为空）。
`statToast` / `affToast` 的分工：状态**已由引擎结算**，`Renderer` 只负责展示——
`affToast` 交给 `toasts.affToast(items, CHARS)` 渲染角色名与增减；
`statToast` 把每条拼成 `真诚 +1` 式的文案后 `toasts.toast(...)`。

`runner.ts` 额外导出 `statText(items)`（把 `[{key, delta}]` 拼成 `真诚 +1　嘴臭 -1`），
抽出来是为了让测试能直接断言资质文案。

## 8. 复读

复读逻辑全在 `effects.ts` 的 `applyRepeat(session)`，可独立测试：

```ts
const last = [...session.history].reverse().find(e => e.kind === 'say' && e.who !== 'me');
if (!last || last.kind !== 'say') return { outcome: 'empty' };
const repeatN = s.lastRepeat === last.text ? s.repeatN + 1 : 1;
const outcome = repeatN >= 3 ? 'banned' : repeatN === 2 ? 'warn' : 'ok';
session.state = { ...s, lastRepeat: last.text, repeatN, water: s.water + 1 };
session.history.push({ kind: 'say', who: 'me', text: last.text });
```

取历史里**最后一条他人（非 `me`）的 `say`** 作为复读对象。三种结果：

| outcome | 条件 | 含义 |
|---------|------|------|
| `empty` | 没有可复读的他人消息 | 无事发生（`spoken` 缺省） |
| `ok` | 首次或换了一句（`repeatN === 1`） | 水群值 +1 |
| `warn` | 连续第 2 次同句（`repeatN === 2`） | 提示将被禁言 |
| `banned` | 连续第 3 次同句（`repeatN >= 3`） | 调用方据此触发 BE24 |

**约定：`applyRepeat` 就地推进传入的 `session`**（改 `session.state` 与 `session.history`，
不返回新对象）。这是硬要求——`main.ts` 与 `run()` 共享同一个对象引用，任何「返回新对象」
的写法都会让两侧永久分叉（复读读到冻结的历史）。

`main.ts` 的复读按钮（`shell.btnRepeat.onclick`）只负责展示与 BE24 分支：先判 `!running`
直接提示；调 `applyRepeat(session)`；`empty` / `spoken === undefined` 时提示；否则
`chat.say('me', result.spoken)` + `updateTop()`。**`banned` 分支**：

```ts
if (result.outcome === 'banned') {
  BGM.set('tension');
  session.state = unlockEnding(session.state, 'b24');   // 就地记入回收室
  writeSlot(AUTOSAVE_ID, snapshotSession());
  overlay.showBE('b24');
  return;
}
```

`warn` / `ok` 分别弹提示。注意 `main.ts` 里复读**不写 `session = result.session`**，
而是直接用就地改好的 `session`。

## 9. 校验器

`validateScript(script, chars, beData)` 返回 `ValidationIssue[]`（`level` 为 `error` / `warn`，
带 `code` 与可选 `index`）。`error` 让构建失败，`warn` 仅提示。逐类检查：

| # | 检查 | code | 级别 | 说明 |
|---|------|------|------|------|
| 1 | 起始 label | `start-missing` / `start-not-first` | error | 必须存在 `start` 标签，且必须在第 0 个节点（`run` 从 `ip=0` 起步） |
| 2 | label 唯一 | `label-duplicate` | error | 同名 label 只允许一次 |
| 3 | 跳转目标 | `goto-unknown` | error | `gotoTargets(n)` 收集的所有去向都必须在 `labels` 里 |
| 3 | 角色键 | `char-unknown` | error | `say` / `card` / `stage`（非 null）的 `who`（`me` 除外）与 `ge` 的 `key` 必须存在于角色表 |
| 3 | BE 文案 | `be-unknown` | error | `be` 的 `id`、`branch` 的 `beWhenAirless` 必须有文案 |
| 3 | hub 去重键 | `hub-id-duplicate` | error | 同一 `hub` 内选项 `id` 不得重复 |
| 3 | loop 去重键 | `loop-id-duplicate` | error | 候选 `pick_<key>`、支线 `seg<i>_<key>`、事件 `ev_<id>` 三类键不得互撞 |
| 3 | loop 支线 | `loop-no-arcs` | error | `arcs` 不得为空 |
| 4 | 可达性 | `unreachable` | warn | 从 `start` 出发到不了的节点 |
| 5 | flag 使用 | `flag-unused` | warn | 被 `set`（含选项 `set`）但从没被「引擎读取」的 flag |

`ENGINE_READ_FLAGS = ['actGood', 'actSkip']` 是白名单：这两个 flag 由引擎侧消费，
即便不在剧本里显式读取也不报 `flag-unused`。

**为什么 `loop` / `branch` 把配置放在节点里？** 它们是**数据驱动的分支节点**，
可选去向写在各自的 `config` 里。`gotoTargets(n)` 因此能把它们像 `choice` 一样展开——
`loop` 收 `candidates[].entry` + 所有 `arcs[].entry` + `events[].entry` + `advance`，
`branch` 收 `Object.values(routes)`。于是校验器**能看见它们的每一条边**，
可达性、跳转目标检查对它们同样生效。

三个辅助函数：

- `buildLabelIndex(script)`：单遍扫描，把每个 `label` 映射到它的下标，得一 `LabelIndex`。
- `gotoTargets(n)`：按 `kind` 收集一个节点的全部去向（`goto` / `choice` / `hub` / `loop` / `branch`，其余为空）。
- `computeReachable(script, labels)`：**顺序扫描 + 跳转闭包**。从 `labels['start']` 入队；
  从某点向后线性推进并标记可达，碰到 `goto` 就把目标入队并停；
  碰到 `choice` / `hub` / `loop` / `branch` 就把所有分支目标入队并停；
  碰到 `be` / `ge` 就停。队列（`pop` 取栈顶的 DFS 形态）保证闭包完整，
  且每个节点至多标记一次。
- `formatIssues(issues)`：`✗` / `⚠` 前缀 + `[code] message（节点 #index）`，逐行拼接。

`validate.cli.ts` 调 `validateScript`，有 error 就 `process.exit(1)`。

## 10. 存档

`persist.ts` 处理存档的序列化与**防御性**反序列化。契约：**任何畸形输入一律返回
`null`，绝不抛错、绝不污染原型**——存档来自 `localStorage`，是不可信输入，
游戏不因坏存档白屏。

### 10.1 序列化格式与版本

```ts
export const SAVE_VERSION = 3;
serializeSession(s) => JSON.stringify({ v: 3, ip, state, history, progress })
```

`v` 是存档版本；`ip` / `state` / `history` / `progress` 即 `Session` 的四个纯 JSON 字段。
`SCHEMA_VERSION = 3` 单独记在 `state.schemaVersion` 里，与 `SAVE_VERSION` 各司其职。
**v3 起新增 `stats` / `target` / `turn` / `unlocked`**（资质与回合循环所需的字段）。

### 10.2 防御性解析

`deserializeSession(raw, scriptLength)` 逐层收窄，任一步不合法即返回 `null`：

- `raw` 必须是对象；`raw.v` 必须 `=== SAVE_VERSION`；`ip` 必须是非负整数且 `<= scriptLength`。
- `parseState`：`aff` 必须含**全部**角色键、值为有限非负数；`stats` 含全部 `STAT_KEYS`；
  `flags` 只认 `FLAG_KEYS`；`hub` 值必须布尔；`unlocked` 是字符串数组（禁 `FORBIDDEN_KEYS`）；
  `water` / `members` / `repeatN` / `turn` 非负整数；`lastRepeat` 字符串；`target` 为 `null` 或合法角色键。
- `parseHistory`：逐条校验，`say` 的 `who` 为 `me` 或合法角色键，`sys` / `note` 有字符串 `text`，否则整份拒绝。
- `parseProgress`：`visited` 值必须为 `true`；`checkpoints` 复用 `parseState` 校验后 `toCheckpoint` 剥掉 `schemaVersion`；`historyLens` 值非负整数。
- **原型污染护栏** `FORBIDDEN_KEYS = {'__proto__', 'constructor', 'prototype'}`：出现在 `flags` / `hub` / `unlocked` / `progress` 的任何键位置一律拒绝。

### 10.3 版本迁移

`migrateSave(raw, scriptLength)` 是迁移入口：

| 输入 `raw.v` | 处理 |
|--------------|------|
| 缺失（裸会话）或 `1` 或 `2` | 展开原对象，`v: SAVE_VERSION`，`state: upgradeState(raw.state)`，`progress` 缺省补 `createInitialProgress()`，再交 `deserializeSession` |
| `=== SAVE_VERSION` | 直接交 `deserializeSession` |
| 其它（含来自未来的版本） | 返回 `null`（宁可读不出，也不按旧规则误读新数据） |

`upgradeState(raw)` 逐字段补齐：`stats` 缺则用 `createInitialState().stats`；
`target` 用 `'target' in raw` 判断（允许显式 `null`）；`turn` 非法则补初值；
`unlocked` 非数组则补初值。即 v1 / v2 老存档会补齐 **`stats` / `target` / `turn` / `unlocked`** 四项。

### 10.4 关键节点快照 + `historyLens`

进度存在 `SessionProgress` 的三个字段里（随存档序列化）：

| 字段 | 含义 |
|------|------|
| `visited` | 已抵达过的 label 集合（`Record<string, true>`） |
| `checkpoints` | **关键节点首次抵达时**的状态快照 `Record<label, CheckpointState>`（无 `schemaVersion`） |
| `historyLens` | 抵达该关键节点时的历史长度 `Record<label, number>` |

`recordArrival(progress, routeMap, label, state, historyLen)` **就地**记进度：
任何 label 都记入 `visited`；若是 `choice` / `hub` 类关键节点**且首次抵达**，
存一份 `toCheckpoint(state)` 快照并把 `historyLens[label]` 记为 `historyLen`。

之所以是「关键节点快照 + historyLens」，是为了**避免读档 / 跳转后消息重复**：
`jumpTo` 把 `ip` 拨回某个 label 再重跑，如果历史不截断，label 与后续 `choice` 之间
夹着的 `say` / `sys` 会被再播一遍。因此 `main.ts` 的 `jumpTo` 会用
`session.history = session.history.slice(0, session.progress.historyLens[label] ?? 0)`
把历史**截断回那一刻**，再用 `fromCheckpoint(checkpoint)` 还原状态；快照刻意取
「抵达 label 那一刻」而不是「抵达后面的 choice 节点时」，正是为了对齐这条截断线。

`fromCheckpoint(cp)` 则把快照补回当前 `schemaVersion`（`{ ...cp, schemaVersion: SCHEMA_VERSION }`），
得到可交还引擎的状态。二者与 `persist.ts` 共用（`parseProgress` 也用 `toCheckpoint`）。
